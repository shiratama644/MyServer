このドキュメントは、サーバーのパフォーマンス向上とデータベース負荷軽減のため、各サービスにRedisキャッシュを導入する際の戦略と実装方法を定めるものです。

### 基本方針：キャッシュアサイド (Cache-Aside) パターン

すべてのキャッシュ実装は、以下の「キャッシュアサイド」パターンを基本とします。

1.  **クライアントからのリクエスト**
2.  **まずRedisキャッシュにデータがあるか確認**する。
3.  **【キャッシュヒット】** データがあれば、Redisからデータを取得してクライアントに返す。（処理完了）
4.  **【キャッシュミス】** データがなければ、**データベース (DB) や外部API**からデータを取得する。
5.  取得したデータを**Redisに保存**する。（次回のリクエストに備える）
6.  クライアントにデータを返す。

### 前提：Redisクライアントの準備

各アプリケーションでは、Redisクライアント（`ioredis`等）を初期化して、使い回せるようにモジュール化しておきます。

**Redis キープレフィックス規則:** 各サイトはキーの先頭にサイト固有のプレフィックスを付け、他のサイトと衝突しないようにする。

| プレフィックス | サイト |
|--------------|--------|
| `dropmod:` | DropMod |
| `flashcard:` | Flashcard |
| `ytdl:` | ytdl |
| `cod:` | cod-web |

### 1. DropMod

#### 1.1. キャッシュ対象
- **Modrinth APIからのMod検索結果:** ユーザーが同じキーワードで検索した際の結果。
- **Modrinth APIからのModメタデータ:** Modの詳細情報、バージョン一覧。

#### 1.2. キャッシュ戦略
- **目的:** 外部APIへのアクセス回数を減らし、応答速度を向上させる。レートリミットのリスクを低減する。
- **TTL (Time To Live / 有効期間):**
    - **検索結果:** **1時間 (3600秒)** に設定。
    - **Modメタデータ:** **6時間 (21600秒)** に設定（Mod情報は比較的安定）。
    - **ローダーバージョン一覧:** **12時間 (43200秒)** に設定（Fabric/Forge等のバージョンは頻繁に変わらない）。
- **キャッシュの更新:** TTLが切れたら自動的に削除されるため、次のアクセス時に最新のデータがAPIから取得され、キャッシュが更新される。積極的な削除は不要。

### 2. ytdl

#### 2.1. キャッシュ対象
- **YouTube API (InnerTube) からの検索結果。**
- **動画メタデータ:** タイトル、説明、サムネイル、ストリームURL等の詳細情報。
- **ホームフィード:** おすすめ動画一覧。
- **コメント一覧。**

#### 2.2. キャッシュ戦略
- **目的:** 外部APIへのアクセス回数を減らし、応答速度を向上させる。
- **TTL:**
    - **ホームフィード:** **15分 (900秒)** （おすすめは比較的頻繁に変わる）。
    - **検索結果:** **1時間 (3600秒)** 。
    - **動画メタデータ（通常動画）:** **6時間 (21600秒)** （動画メタデータはほぼ不変）。
    - **動画メタデータ（ライブ配信）:** **キャッシュしない** （リアルタイム性が最重要のため）。
    - **コメント:** **5分 (300秒)** 。
- **キャッシュの更新:** TTLによる自動失効を基本とする。

---

### 3. Flashcard

#### 3.1. キャッシュ対象
- **公開ワードリスト一覧ページ。**
- **カテゴリ一覧。**

#### 3.2. キャッシュ戦略
- **目的:** 全ユーザー共通のコンテンツのDB負荷を軽減。
- **TTL:** **1時間 (3600秒)**。
- **キャッシュの更新（重要）:** 新しいワードリストが投稿・編集・削除された場合、**関連するキャッシュを能動的に削除（無効化）する**必要がある。
