# 開発時の注意点

このドキュメントは、各サイトの開発・デプロイ時に **はまりがちな落とし穴** や **事前に知っておくべきこと** をまとめたものです。必ず一読してから開発を始めてください。

---

## 1. Next.js 共通

### basePath の設定（必須）

パスベースでルーティングするため、**ルート (`/`) で動く Portfolio 以外の全サイト** で `basePath` の設定が必要です。

```js
// next.config.js (例: DropMod)
module.exports = {
  basePath: '/dropmod',
  output: 'standalone',
}
```

**注意点:**
- `basePath` を設定すると、`next/link` の `<Link href="/about">` は自動的に `/dropmod/about` に変換される
- ただし **`public/` フォルダ内の静的ファイル**（画像等）は自動変換されない。手動で `${basePath}/images/...` のようにプレフィックスを付ける必要がある
- `next/image` コンポーネントの `src` にも basePath を手動で付ける必要がある
- **開発時 (`npm run dev`) も basePath が有効になる** ので、ローカル開発では `localhost:3000/dropmod/` にアクセスする必要がある
- `assetPrefix` も併用すると、静的アセット（CSS/JS）のパスも修正される

### Next.js 16 の破壊的変更

- **`middleware.ts` → `proxy.ts` に改名:** Next.js 16 では `middleware.ts` が `proxy.ts` に改名された。認証ミドルウェアを書く場合は `proxy.ts` を使用すること
- **`output: 'standalone'`:** PM2 で `next start` を使う場合は `standalone` を推奨。`.next/standalone/` に最小限のファイルが出力される

### 環境変数

- クライアントサイドで使う環境変数は `NEXT_PUBLIC_` プレフィックスが必須
- サーバーサイドのみの環境変数（APIキー等）には `NEXT_PUBLIC_` を付けない

## 2. 認証（Better Auth）

### NextAuth.js は使わない

**Auth.js（旧 NextAuth.js）v5 はメンテナンスモード** に入っています。新プロジェクトでは **Better Auth** を使用してください。

| 項目 | Auth.js v5 | Better Auth |
|------|-----------|-------------|
| 状態 | メンテナンスモード（セキュリティパッチのみ） | アクティブ開発中 |
| 推奨 | 既存プロジェクトの維持 | 新プロジェクト |
| 環境変数 | `AUTH_*` | `AUTH_*` |
| Next.js 16 | `proxy.ts` 対応に手間 | ネイティブ対応 |

### Better Auth の設定例

```ts
// lib/auth.ts
import { betterAuth } from 'better-auth'

export const auth = betterAuth({
  socialProviders: {
    google: {
      clientId: process.env.AUTH_GOOGLE_ID!,
      clientSecret: process.env.AUTH_GOOGLE_SECRET!,
    },
  },
  // ...
})
```

**注意:**
- 環境変数は `AUTH_` プレフィックスを使用（`NEXTAUTH_` は古い）
- Dashboard の Google 認証では、特定のメールアドレスのみ許可するフィルタリングが必要

## 3. PM2 + Bun

### PM2 で Bun アプリを管理する

cod-web は Bun を使用しますが、PM2 v7 で正式対応済みです。

```js
// ecosystem.config.js (app コンテナ用)
module.exports = {
  apps: [
    // Next.js アプリ（Node.js）
    { name: 'portfolio',  script: 'next', args: 'start', cwd: '/srv/portfolio',  interpreter: 'node' },
    { name: 'dropmod',    script: 'next', args: 'start', cwd: '/srv/dropmod',    interpreter: 'node' },
    { name: 'flashcard',  script: 'next', args: 'start', cwd: '/srv/flashcard',  interpreter: 'node' },
    { name: 'ytdl',       script: 'next', args: 'start', cwd: '/srv/ytdl',       interpreter: 'node' },
    { name: 'dashboard',  script: 'next', args: 'start', cwd: '/srv/dashboard',  interpreter: 'node' },
    { name: 'palmide',    script: 'next', args: 'start', cwd: '/srv/palmide',    interpreter: 'node' },
    // Bun アプリ（game コンテナ用）
    { name: 'cod-web',    script: 'bun',  args: 'run start', cwd: '/srv/cod-web', interpreter: 'bun' },
  ],
}
```

**注意点:**
- `.ts` ファイルは `pm2 start app.ts` で自動的に Bun を使用
- `.js` ファイルで Bun を使う場合は `--interpreter bun` を明示的に指定
- **PM2 デーモンは最初に起動したランタイムを維持する** ので、Node と Bun を混在させる場合は `pm2 kill` でリセットしてから再起動
- クラスタモードは Bun >= 1.1.25 が必要
- `pm2 save && pm2 startup` でサーバー再起動後も自動復旧

## 4. Nginx 設定

### WebSocket を使うサイト（Dashboard, cod-web）

以下の3つが **必須** です。1つでも抜けると WebSocket が接続できません：

1. `proxy_http_version 1.1;`
2. `proxy_set_header Upgrade $http_upgrade;`
3. `proxy_set_header Connection $connection_upgrade;`

さらに、**`nginx.conf` の `http {}` ブロック内** に `map` の定義が必要：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

### Socket.IO 固有の設定

Dashboard は Socket.IO を使うため、以下の追加設定を推奨：
- `proxy_buffering off;` — リアルタイムデータのバッファリングを無効化
- `proxy_cache off;` — キャッシュを無効化
- `proxy_read_timeout 86400s;` — 24時間のタイムアウト（長時間接続を維持）

### proxy_pass の末尾スラッシュ

```nginx
# ✅ 正しい: /dropmod/ の部分が取り除かれて転送される
location /dropmod/ {
    proxy_pass http://10.10.10.101:3001/;
}

# ❌ 間違い: /dropmod/ がそのままバックエンドに渡される
location /dropmod/ {
    proxy_pass http://10.10.10.101:3001;
}
```

末尾に `/` があるかないかで動作が変わるので注意。

## 5. ネットワーク（vmbr0 / vmbr1）

### vmbr1 コンテナから外部APIにアクセスできない

app コンテナ（vmbr1）は **外部ネットワークに直接アクセスできません**。しかし、以下のサイトは外部APIへのアクセスが必要です：

| サイト | 必要な外部アクセス |
|--------|-----------------|
| DropMod | Modrinth API |
| ytdl | YouTube (InnerTube) API |
| Flashcard | 課金API (Stripe等) |
| PalmIDE | Gemini API（ただしクライアントから直接の可能性あり） |

**解決策:** Proxmox ホストで **NAT（マスカレード）** を設定する必要があります。

```bash
# /etc/network/interfaces または iptables で設定
# vmbr1 → vmbr0 へのNATを有効化
iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o vmbr0 -j MASQUERADE

# 永続化
apt install iptables-persistent
netfilter-persistent save
```

### db コンテナのポートは外部に公開しない

PostgreSQL (`:5432`) と Redis (`:6379`) は **vmbr1 内からのみアクセス可能** です。外部からは絶対にアクセスできません。これはセキュリティ上正しい構成です。

## 6. Redis

### キープレフィックスの厳守

複数サイトが同じ Redis を共有するため、**必ずサイト固有のプレフィックス** を付けてください。

```
dropmod:cache:search:q=...
ytdl:cache:video:abc123
flashcard:cache:wordlist:1
cod:cache:leaderboard
```

プレフィックスを付けないと、他のサイトのキャッシュと衝突して **データがおかしくなります**。

### ioredis の接続設定

```ts
// lib/redis.ts
import Redis from 'ioredis'

const redis = new Redis({
  host: '10.10.10.102',  // db コンテナのIP (vmbr1)
  port: 6379,
})

export default redis
```

## 7. PostgreSQL

### データベースの分離

各サイトが **別のデータベース** を使うようにしてください。同じDBを共有すると、テーブル名の衝突や権限の問題が起きます。

| サイト | データベース名 |
|--------|-------------|
| Flashcard | `flashcard_db` |
| ytdl | `ytdl_db` |
| cod-web | `cod_db` |
| Dashboard | `admin_db` |

### 接続設定

```
postgresql://flashcard_user:password@10.10.10.102:5432/flashcard_db
```

## 8. SSL証明書（Let's Encrypt）

### MyDNS.jp の制約

- **DNS-01 チャレンジは使えません**（MyDNS.jp が DNS API を提供していないため）
- **HTTP-01 チャレンジ（webroot方式）** を使用
- 証明書取得時はポート80が外部からアクセス可能である必要がある

### 証明書更新の自動化

```bash
# cron で1日2回チェック
0 3,15 * * * certbot renew --quiet --post-hook "nginx -s reload"
```

## 9. サイト固有の注意点

### DropMod
- クライアントサイドの永続化に **IndexedDB (Dexie)** を使用
- サーバー側は Modrinth API のキャッシュ（Redis）のみ
- `pnpm` をパッケージマネージャとして使用（`npm` ではない）

### ytdl
- **ffmpeg のインストールが必須:** `apt install ffmpeg`
- 大きなファイルのダウンロードを扱うため、Nginx の `client_max_body_size` を大きめに設定
- `youtubei.js` (v18.x) を使用。`Innertube.create()` でシングルトンクライアントを作成

### Flashcard
- **Next.js への移行がまだ完了していない** — 移行が先決
- Stripe 等の課金システム導入予定 — Webhook エンドポイントが必要
- HTTPS が必須（Stripe の要件）

### cod-web (game コンテナ)
- **Bun** ランタイムを使用（Node.js ではない）
- ゲームサーバーは **WebSocket (:8080)** で通信
- リアルタイムゲームデータは **絶対にキャッシュしない**
- app コンテナとは別コンテナでリソースを分離

### PalmIDE
- クライアントサイド中心のアプリ（IndexedDB + Gemini API BYOK）
- サーバー側のDBは不要の可能性が高い
- Gemini API はユーザーのブラウザから直接通信（BYOK = Bring Your Own Key）

### Dashboard
- Proxmox の管理コマンド (`pct`, `qm`) を実行するため、**sudo 権限の設定** が必要
- `node-pty` はネイティブモジュールなので、ビルドツール (`build-essential`, `python3`) のインストールが必要
- セキュリティ上、最も慎重に実装すべきサイト

### Portfolio
- SSG (静的サイト生成) なので、Nginx で静的ファイルを直接配信することも可能
- PM2 でのプロセス管理は不要（ただし現在は統一のため PM2 で管理）
- Three.js の3D描画はクライアントサイドのみ

## 10. デプロイフロー

### 共通の手順

```bash
# 1. リポジトリをクローン（または pull）
cd /srv/<site>
git pull origin main

# 2. 依存パッケージをインストール
pnpm install   # または npm install / bun install

# 3. ビルド
pnpm build     # または npm run build / bun run build

# 4. PM2 で再起動
pm2 restart <site-name>

# 5. 動作確認
curl http://localhost:<port>/
```

### 初回デプロイ時のみ

```bash
# .env ファイルの作成（DB接続情報、APIキー等）
cp .env.example .env
nano .env

# データベースのマイグレーション（必要なサイトのみ）
pnpm db:migrate

# PM2 に登録
pm2 start ecosystem.config.js
pm2 save
pm2 startup
```

## 11. セキュリティチェックリスト

- [ ] `.env` ファイルは `.gitignore` で除外
- [ ] DB のパスワードは環境変数で管理（ハードコーディング禁止）
- [ ] API キーはサーバーサイドの環境変数のみ（`NEXT_PUBLIC_` を付けない）
- [ ] SSH は鍵認証のみ（パスワード認証は無効化）
- [ ] ファイアウォール (UFW) で不要なポートを閉じる
- [ ] Nginx のセキュリティヘッダーを設定（HSTS, X-Frame-Options 等）
- [ ] SSL (HTTPS) を有効化
- [ ] PostgreSQL / Redis は vmbr1 内からのみアクセス可能
- [ ] `sudo` 権限は最小限に（`visudo` で特定コマンドのみ許可）
